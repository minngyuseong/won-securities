# 주요 설계 의사결정

### 1. 부분체결을 고려한 주문·체결 구조
문제 상황
하나의 지정가 주문이 여러 번 나누어 체결될 수 있어 부분체결 내역을 관리할 구조 필요.
결정
주문 정보는 STOCK_ORDER에 저장하고 실제 체결 내역은 TRADE_EXECUTION에 별도로 저장. 하나의 주문에 여러 체결 내역을 연결할 수 있도록 구성함.
판단 근거
주문가격과 주문수량은 주문 시 정해지지만 실제 체결가격과 체결수량은 체결마다 달라질 수 있음. 주문과 체결을 분리해 부분체결이 발생할 때마다 실제 체결 내역을 추가할 수 있도록 함.

### 2. 미체결 주문을 반영한 주문 가능 금액·수량 계산
문제 상황
현재 예수금과 보유수량만 기준으로 계산하면 이미 접수된 미체결 주문에 사용 중인 금액이나 수량까지 다시 주문할 수 있음.
결정
접수 또는 부분체결 상태인 주문의 남은 금액과 수량을 반영해 실제 주문 가능 금액과 수량을 조회하도록 쿼리 구성.
판단 근거
미체결수량은 주문수량 - 누적 체결수량으로 계산. 관련 데이터가 보유잔고·주문·체결 테이블에 나뉘어 있어 각각 조회해 애플리케이션에서 계산하기보다 DB에서 JOIN과 집계 후 필요한 결과만 조회하도록 함.

### 3. 현재 데이터와 이력 데이터의 관리 기준
문제 상황
전량 매도나 상장폐지처럼 현재 거래에서 사용되지 않는 데이터의 삭제 여부에 대한 기준 필요.
결정
보유수량이 0이 된 HOLDING_BALANCE는 삭제. 상장폐지된 종목은 STOCK_ITEM에서 삭제하지 않고 DELISTED 상태로 유지.
판단 근거
HOLDING_BALANCE는 현재 보유 상태를 관리하므로 보유수량이 없는 데이터는 삭제 가능. 종목 정보는 과거 주문과 체결 내역에서도 참조하므로 삭제하지 않고 상태값으로 관리함.
